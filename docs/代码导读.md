## 〇、先建立全局观：两条主链路

整个后端可以看成**两条主链路**，其余模块都是围绕这两条链路的「配料」：

### 链路 A：一次建库链路（离线、人工触发、可重复跑）

把数据库里的**表格行**，变成向量库里的**可检索知识块**：

```
业务数据库（MySQL / 本机 PG 副本）
   │  ① db.py / pg_source.py  只读连接、读表结构、流式逐行读数据
   ▼
documents.py   表格行  →  「字段: 值」自然语言文本（超长则切块）
   ▼
bm25.py        jieba 分词 → 建 BM25 索引（稀疏向量）
embeddings.py  文本 → bge-small-zh-v1.5 稠密向量（512 维）
   ▼
vector_store.py  稠密 + 稀疏一起写进 Qdrant 本地嵌入式库
   ▲
ingest.py 是这条链路的「总指挥」（run_ingest / run_incremental），
main.py 的 /api/ingest 或命令行 backend/app/ingest.py 触发它。
```

### 链路 B：一次问答链路（在线、每次提问都跑一遍）

从用户提问，到带来源、带引用校验的流式回答：

```
用户提问（前端）
   ▼  ② main.py（/api/chat 或 /api/agent/chat）
[可能命中] answer_cache.py  规范化精确匹配缓存 → 直接回放旧答案
   ▼
retriever.py   ① 两路召回：embeddings.py 稠密 + bm25.py 稀疏
               ② rrf_fuse 按排名融合（RRF）
   ▼
rerank.py      ③ 大模型读一遍候选片段，二次排序（失败自动退回 RRF 原序）
   ▼
rag.py / agent.py / deep_agent.py   ④ 拼提示词 → llm.py 调大模型 → 流式吐字
   ▼
citation.py    ⑤ 校验回答里的 [参考资料N] 与数字有没有依据（越界引用会被删掉）
   ▼
main.py   以 SSE 事件流推给前端   →   history.py 落库 / metrics.py 记指标
```

> **阅读顺序说明**：下面的「模块逐个解读」严格按你给定的顺序排列（不是按链路排）。
> 每个模块都会标注它**属于哪条链路**（建库 / 问答 / 两者 / 支撑），
> 这样你既能按顺序读，又能随时把它挂回上面这两条线上。

**贯穿全项目的三个「设计母题」**（几乎每个模块都能看到它们的影子）：

1. **降级而不崩溃**：任何外部依赖（大模型 / PG / Neo4j / Tavily / 向量库）没配好或报错，
   都不是抛异常让服务挂掉，而是「跳过这个功能、用更弱的模式继续服务」。
2. **只读保护**：凡是让大模型生成 SQL / Cypher 去查库的地方，都有多层「只读 + 单语句 + 强制 LIMIT」防护。
3. **可解释 / 可溯源**：答案要带来源卡片、要能校验引用，不要「一本正经地胡说」。

## 模块逐个解读（按给定阅读顺序）

### 1. `backend/app/config.py` —— 全项目配置总控台
**链路归属：两者（所有模块都向它要配置）**

- **一句话职责**：从项目根目录 `.env` 读进所有配置、做类型转换，打包成一个不可变的 `Settings` 快照，全项目共享。
- **关键函数**：

  | 函数 | 签名 | 输入 | 输出 |
  |---|---|---|---|
  | `_str` | `_str(key: str, default: str = "") -> str` | 环境变量键名、默认值 | 去掉首尾空白的字符串（读不到/空白则给默认值） |
  | `_int` | `_int(key: str, default: int) -> int` | 键名、默认整数 | 整数（解析失败回落默认值，不报错） |
  | `_float` | `_float(key: str, default: float) -> float` | 键名、默认小数 | 小数 |
  | `_bool` | `_bool(key: str, default: bool) -> bool` | 键名、默认真假值 | 布尔（认 `1/true/yes/on`、`0/false/no/off`，其余回落默认） |
  | `_path` | `_path(key: str, default: str) -> Path` | 键名、默认相对路径 | `Path` 绝对路径（相对路径一律以项目根目录为基准） |
  | `_parse_table_labels` | `_parse_table_labels(raw: str) -> dict[str, str]` | `"表名=中文名,表名=中文名"` | 表名→中文展示名字典 |
  | `_parse_primary_keys` | `_parse_primary_keys(raw: str) -> dict[str, str]` | `"表名=列名,..."` | 表名→兜底主键列名字典 |
  | `Settings` | `@dataclass(frozen=True) class Settings` | —— | 约 90 个字段的不可变配置对象 |
  | `_build_settings` | `_build_settings() -> Settings` | —— | 组装好的 `Settings` |
  | `get_settings` | `get_settings() -> Settings`（`@lru_cache(maxsize=1)`） | —— | 全局唯一配置快照 |

  关键常量：`PROJECT_ROOT = Path(__file__).resolve().parents[2]`、`ENV_FILE = PROJECT_ROOT / ".env"`、
  `DEFAULT_TABLE_LABELS = {"bidding_notices": "招标公告", "bidding_project": "招投标项目", "companies": "公司信息"}`。
  `Settings` 上的关键属性：`llm_configured`、`rerank_configured`、`agent_configured`、`pg_configured`、
  `graph_configured`、`web_search_configured`、`vision_configured`、`history_configured`、`mysql_configured`、
  `llm_display_name`、`rerank_model_or_default`、`label_of(table)`、`kb_source_is_postgres`。

  几个**默认值**（已逐一核对源码）：`retrieve_dense_top_k=10`、`retrieve_sparse_top_k=10`、
  `retrieve_final_top_k=5`、`rrf_k=60`、`dense_min_score=0.35`、`rerank_candidates=10`、
  `rerank_max_chars=300`、`rerank_timeout=45`、`max_doc_chars=1200`、`chunk_size=500`、`chunk_overlap=80`、
  `llm_temperature=0.2`、`llm_max_tokens=1024`、`agent_max_tokens=2048`、`agent_max_steps=6`、
  `embed_batch_size=32`、`vision_model="glm-4.6v-flashx"`、`cache_ttl=3600`、`auth_pbkdf2_iterations=200000`。

- **上游 / 下游**：上游是「操作系统的环境变量 + `.env` 文件」；下游是全项目几乎所有模块
  （`db.py`、`retriever.py`、`llm.py`、`main.py`……都 `from .config import get_settings`）。
- **为什么这么设计**：
  - 配置与代码分离（改配置不改代码、密钥不进 Git）；
  - `frozen=True` + `lru_cache`：配置只从磁盘读一次、创建后不可改，避免「运行到一半配置变了」的诡异问题；
  - 容错优于报错：某个值写错不导致服务起不来，退回默认值，运维可通过 `/api/config` 发现「没生效」；
  - 相对路径统一以项目根目录解析，保证「从哪个目录启动都指向同一个文件」。
- **读这一遍必须能回答的面试问题**：
  1. `.env` 里的值都是字符串，程序是怎么把它变成整数/布尔/路径的？写错了会怎样？
  2. 为什么配置对象要 `frozen=True`，还要用 `lru_cache` 缓存？
  3. 一堆 `xxx_configured` 属性是干什么的？它和「降级」有什么关系？

### 2. `backend/app/db.py` ＋ `backend/app/pg_source.py` —— 建库数据源（两套同接口实现）
**链路归属：建库链路**

- **一句话职责**：`db.py` 负责只读连接 MySQL、读表结构、流式逐行取数；`pg_source.py` 是它在 PostgreSQL 上的「同名同接口孪生兄弟」，让建库管道可以只换数据源、不改下游逻辑。
- **关键函数（db.py）**：

  | 函数 | 签名 | 输入 | 输出 |
  |---|---|---|---|
  | `quote_ident` | `quote_ident(name: str) -> str` | 表名/列名 | 反引号包裹的安全标识符（`_SAFE_IDENT` 校验） |
  | `mysql_connection` | `mysql_connection(settings: Settings | None = None) -> Iterator[pymysql.connections.Connection]`（`@contextmanager`） | 配置 | 上下文管理器，`with` 内给你一个连接、用完自动关 |
  | `normalize_value` | `normalize_value(value: Any) -> Any` | 数据库取回的原始值 | 可 JSON 化的值（如 `Decimal`→`float`、`datetime`→字符串） |
  | `normalize_row` | `normalize_row(row: dict[str, Any]) -> dict[str, Any]` | 一行原始字典 | 每个值都规范过的一行 |
  | `discover_schema` | `discover_schema(conn, tables: tuple[str, ...]) -> dict[str, dict]` | 连接、要读的表名元组 | 表 → {列定义 / 主键 / 行数} |
  | `iter_rows` | `iter_rows(...)` | 连接、表、列 …… | **流式迭代器**，一行一行吐（用 `SSDictCursor`） |
  | `describe_columns` | `describe_columns(conn, table: str) -> dict[str, str]` | 连接、表名 | 列名→列注释 |
  | `list_tables` | `list_tables(conn) -> list[dict[str, Any]]` | 连接 | 库内所有表 |
  | `DatabaseUnavailable` | `class DatabaseUnavailable(RuntimeError)` | —— | 连不上库时抛的异常 |

  **pg_source.py** 提供同名的 `pg_connection(settings=None)`、`discover_schema(...)`、`iter_rows(...)`，
  外加 `_current_schema`、`_column_type_text`、`_normalize_value`、`_primary_key_columns(conn, schema, table)`。

- **上游 / 下游**：上游是 `ingest.py`（建库总指挥）按 `KB_SOURCE`（`mysql`/`postgres`）二选一调用；
  下游是 `documents.py`（拿到行去渲染文本）。`main.py` 的 `/api/mysql/schema` 也用 `db.py` 读实时结构。
- **为什么这么设计**：
  - 用**迭代器**逐行读，而不是一次读成列表——表可能有几十万行，一次性读进内存会撑爆；
  - 「同接口孪生」——只要 `pg_source` 返回的数据形状和 `db.py` 一模一样，下游一行都不用改
    （这就是「依赖倒置」的土办法：下游只依赖「能给我这些函数的对象」，不依赖具体数据库）；
  - `normalize_value` 统一把数据库专有类型转成通用类型，避免 `Decimal`、`datetime` 等在后续 JSON 化时炸掉。
- **读这一遍必须能回答的面试问题**：
  1. 为什么建库时要「流式逐行读」而不是 `SELECT *` 后一次取回？
  2. `db.py` 和 `pg_source.py` 为什么要保持「同名同接口」？这样有什么好处？
  3. `quote_ident` 和 `normalize_value` 各自在防什么问题？

### 3. `backend/app/documents.py` —— 表格行 → 可检索文本
**链路归属：建库链路**

- **一句话职责**：把一行数据库记录渲染成「【中文表名】记录ID：xxx / 字段: 值……」这样一段自然语言文本，太长再切块，产出 `Document` 对象供检索用。
- **关键函数**：

  | 函数 | 签名 | 输入 | 输出 |
  |---|---|---|---|
  | `render_row` | `render_row(row: dict[str, Any], columns: list[dict[str, Any]], label: str, primary_key: Any) -> str` | 一行数据、列定义、中文表名、主键值 | 一段「字段: 值」多行文本（第一行是抬头） |
  | `split_text` | `split_text(text: str, chunk_size: int, overlap: int) -> list[str]` | 长文本、块大小、重叠 | 切好的文本块列表 |
  | `_truncate_fields` | `_truncate_fields(row: dict[str, Any]) -> dict[str, Any]` | 一行 | 单个字段超长被截断后的一行 |
  | `build_documents` | `build_documents(rows: Iterator[dict[str, Any]], columns, table: str, label: str, settings: Settings, primary_key_column: str | None = None) -> Iterator[Document]` | 行迭代器、列定义、表名、中文名、配置、主键列名 | 「随用随产」的 `Document` 生成器 |

  `Document` 是一个 `@dataclass`，字段：`doc_id`、`table`、`label`、`primary_key`、`chunk_index`、`chunk_total`、`text`、`payload`。
  两个模块常量：`_FIELD_TEXT_LIMIT = 4000`（单字段文本上限）、`_SKIP_TYPES`（二进制等要跳过的列类型）。

- **上游 / 下游**：上游是 `ingest.py`（把 `iter_rows` 的行喂进来）；下游是 `bm25.py`、`embeddings.py`、`vector_store.py`（拿 `Document.text` 去分词/向量化/入库）。
- **为什么这么设计**：
  - 表格行本身不是「句子」，直接喂给语义模型效果差；渲染成带中文列名的自然语言，检索效果更好；
  - 抬头写「【表名】记录ID」让每段文字自带**溯源信息**；
  - 按 `columns`（表结构）而不是 `row` 的键顺序渲染，保证「同样的数据每次生成同样的文字」——这对重跑建库保持内容一致很关键；
  - 跳过二进制列（`_SKIP_TYPES`），否则转成文字只会是乱码噪声；
  - `doc_id` 由「表名:主键值:块号」组成（主键缺失时退化成行号，见第 4 节的告警机制），保证幂等。
- **读这一遍必须能回答的面试问题**：
  1. 为什么不直接拿数据库的 `json` 存进向量库，而要「文档化」成自然语言？
  2. `build_documents` 为什么返回生成器而不是 `list`？主键取不到时会怎样？
  3. 长文本为什么要「切块 + 重叠」？

### 4. `backend/app/ingest.py` —— 建库总指挥
**链路归属：建库链路（并把你引向 embeddings / history / auth / vision 之外的 `run_ingest`）**

- **一句话职责**：串起「读数据源 → 文档化 → 建 BM25 → 向量化 → 写 Qdrant」，支持全量重建与增量更新，并一路汇报进度。
- **关键函数**：

  | 函数 | 签名 | 输入 | 输出 |
  |---|---|---|---|
  | `_columns_for_docs` | `_columns_for_docs(columns: list[dict[str, Any]]) -> list[dict[str, Any]]` | 原始列定义 | 只保留文档化需要的列定义 |
  | `generate_documents` | `generate_documents(settings=None, progress: ProgressFn | None = None) -> tuple[list[Document], list[list[str]], dict[str, Any]]` | 配置、进度回调 | (全部文档, 每篇的 jieba 词元, 本阶段报告)——**只读，不写向量库** |
  | `run_ingest` | `run_ingest(settings=None, recreate: bool = True, progress: ProgressFn | None = None, mode: str = "full") -> dict[str, Any]` | 配置、是否清库重建、进度回调、模式 | 结构化建库报告 |
  | `run_incremental` | `run_incremental(settings=None, progress: ProgressFn | None = None) -> dict[str, Any]` | 配置、进度回调 | 增量报告（含 `added/updated/deleted/unchanged`） |
  | `main` | `main() -> None` | —— | 命令行入口（直接 `python -m app.ingest` 建库） |

  关键常量 `_EMBED_BATCH = 64`（向量化分批大小）；类型别名 `ProgressFn = Callable[..., None]`。

- **上游 / 下游**：上游是 `main.py` 的 `/api/ingest`（后台线程）或命令行 `python -m app.ingest`；
  下游是 `db.py`/`pg_source.py` → `documents.py` → `bm25.py` → `embeddings.py` → `vector_store.py`。
- **为什么这么设计**：
  - `mode` 默认 `"full"`，保证老调用方（不传 mode）行为完全不变（**向后兼容**）；
  - 增量更新靠「内容指纹」比对，只写新增/变更的块、最后删掉数据源已消失的旧块（写入在前、删除在后，避免中途失败造成空档）；
  - Qdrant 本地嵌入式是**单进程独占**，所以建库只能用「后台线程 + 进程内锁」串行化（见 6 节 `vector_store`）；
  - 进度用回调函数 `progress(stage, message, **extra)` 上报，`main.py` 把它转成前端能看的日志。
- **读这一遍必须能回答的面试问题**：
  1. 全量重建和增量更新的区别是什么？增量为什么「先写后删」？
  2. `run_ingest` 为什么不把 `mode` 的默认值设成 `incremental`？
  3. 为什么建库不能开多进程/多 worker？

### 5. `backend/app/bm25.py` —— 自建 BM25 关键词检索
**链路归属：两者（建库时建索引，问答时查索引）**

- **一句话职责**：用 jieba 分词，手写一个 BM25 打分器，把「词 → 稀疏向量」编码出来，供建库时存进向量库、问答时做关键词召回。
- **关键函数**：

  | 函数 / 方法 | 签名 | 输入 | 输出 |
  |---|---|---|---|
  | `tokenize` | `tokenize(text: str) -> list[str]` | 任意文本 | jieba 切好并过滤后的词元列表（`_TOKEN_KEEP` 控制保留规则） |
  | `BM25Index.__init__` | `__init__(self, k1: float = 1.5, b: float = 0.75) -> None` | BM25 两个可调参数 | 索引对象 |
  | `BM25Index.fit` | `fit(self, token_lists: list[list[str]]) -> "BM25Index"` | 每篇文档的词元列表 | 拟合好的自己（算出词表、IDF、平均文档长度） |
  | `BM25Index.ready` | `ready`（属性）`-> bool` | —— | 是否已拟合可用 |
  | `BM25Index.idf` | `idf(self, term: str) -> float` | 一个词 | 该词的 IDF 值 |
  | `BM25Index.encode_document` | `encode_document(self, tokens: list[str]) -> tuple[list[int], list[float]]` | 一篇文档的词元 | （词 id 下标列表, 对应权重列表）——稀疏向量 |
  | `BM25Index.encode_query` | `encode_query(self, text: str) -> tuple[list[int], list[float]]` | 查询文本 | 查询的稀疏向量 |
  | `BM25Index.to_dict` | `to_dict(self) -> dict` | —— | 可序列化的字典 |
  | `BM25Index.save` | `save(self, path: Path) -> None` | 保存路径 | 写入磁盘（无返回） |
  | `BM25Index.load` | `load(cls, path: Path, k1: float = 1.5, b: float = 0.75) -> "BM25Index"`（类方法） | 路径、参数 | 从磁盘加载的索引 |

- **上游 / 下游**：上游是 `ingest.py`（`fit` 建索引）与 `retriever.py` 的 `load_bm25`；
  下游是 `vector_store.py`（稀疏向量写入 / 查询 Qdrant）。
- **为什么这么设计**：
  - 语义模型对「公司名、项目编号」这类精确词反而不准，BM25 补齐这块；自建实现零额外依赖、可持久化、完全可控；
  - 稀疏向量用「词 id 下标 + 权重」表示，正好对齐 Qdrant 的稀疏向量格式；
  - 索引可 `save/load`，避免每次问答都重建。
- **读这一遍必须能回答的面试问题**：
  1. BM25 的 `k1` 和 `b` 分别控制什么？（词频饱和度 / 文档长度归一化）
  2. 为什么中文要先 jieba 分词？「稀疏向量」和「稠密向量」的区别是什么？
  3. 为什么检索要用「稠密 + 稀疏」两路，而不是只留一路？

### 6. `backend/app/embeddings.py` —— 稠密向量模型封装

### 8. `backend/app/retriever.py` —— 混合检索 + RRF 融合
**链路归属：问答链路（核心）**

- **一句话职责**：一次问答里，同时跑「向量路」和「BM25 路」两路召回，再用 RRF 按排名融合成一份候选列表。
- **关键函数**：

  | 函数 / 类 | 签名 | 输入 | 输出 |
  |---|---|---|---|
  | `load_bm25` | `load_bm25(settings: Settings | None = None) -> BM25Index` | 配置 | BM25 索引（按文件 mtime 做缓存，文件变了才重载） |
  | `RetrievalResult` | `@dataclass class RetrievalResult` | 字段：`question`、`hits` | 检索结果盒子；方法 `to_sources(text_limit=900)` 转成前端来源 |
  | `rrf_fuse` | `rrf_fuse(result_lists: list[tuple[str, list[dict[str, Any]]]], rrf_k: int, final_k: int, dense_min_score: float = 0.0) -> list[dict[str, Any]]` | 多路命中（带路名）、RRF 常数 k、最终条数、向量门槛 | 融合并去重后的候选列表 |
  | `retrieve` | `retrieve(question: str, settings=None, store=None, embedder=None, bm25=None, final_k: int | None = None) -> RetrievalResult` | 问题、（可注入的）依赖 | 检索结果（库空时返回空结果，不抛异常） |

- **上游 / 下游**：上游是 `rag.py`（`/api/chat`）与 `agent.py`（检索工具）；
  下游是 `embeddings.py`、`bm25.py`、`vector_store.py`。
  （`rerank.py` 是它的「下一道工序」，但由上层决定要不要调用。）
- **为什么这么设计**：
  - RRF 公式 `score(d) = Σ 1/(k + rank)` **只依赖排名、不依赖分数**，免去了「向量余弦分」和「BM25 分」量纲不同、无法直接相加的难题；
  - `rrf_k=60` 是业界常用默认；`dense_min_score=0.35` 是召回门槛——余弦相似度天然会给每个问题都返回 top-k，
    哪怕问的是完全无关的内容，所以要「被 BM25 命中 **或** 向量相似度达标」才算有效来源，否则会把无关公告硬塞给模型导致编造；
  - dense 路整体包了 `try/except`，向量模型不可用时降级为空，BM25 路仍能工作；
  - `load_bm25` 用文件修改时间做缓存，避免每次提问都重新加载/重建索引。
- **读这一遍必须能回答的面试问题**：
  1. 为什么融合用 RRF 而不是「加权求和」？RRF 的公式是什么？
  2. `dense_min_score` 门槛是为了防什么？设成 0 会怎样？
  3. 向量路挂了，检索还能工作吗？为什么？

### 9. `backend/app/rerank.py` —— 大模型二次排序
**链路归属：问答链路**

- **一句话职责**：让大模型真的读一遍候选片段，按相关度二次排序；任何失败都自动退回 RRF 原序，绝不抛异常。
- **关键函数**：

  | 函数 | 签名 | 输入 | 输出 |
  |---|---|---|---|
  | `_summarize` | `_summarize(hit: dict[str, Any], max_chars: int) -> str` | 一条命中、最大字符数 | 压缩后的片段摘要（省 token） |
  | `build_rerank_messages` | `build_rerank_messages(...)` | 问题、候选摘要、条数 | 发给模型的消息列表 |
  | `extract_json` | `extract_json(raw: str) -> Any | None` | 模型原始输出 | 解析出的 JSON（失败返回 None） |
  | `parse_order` | `parse_order(raw: str, n: int) -> list[int] | None` | 模型输出、候选数 | 排序序号数组（失败返回 None） |
  | `rerank_hits` | `rerank_hits(question: str, hits: list[dict[str, Any]], settings=None, top_k: int | None = None) -> tuple[list[dict[str, Any]], dict[str, Any]]` | 问题、RRF 候选、配置、条数 | (新顺序的命中列表, meta) |

  meta 字段：`rerank_applied` / `rerank_model` / `rerank_candidates` / `rerank_error`。
  常量：`RERANK_SYSTEM_PROMPT`、`_RERANK_MAX_TOKENS=3072`、`_FENCE_RE`、`_JSON_RE`、`_ORDER_KEYS`、`_extract_sequence`。

- **上游 / 下游**：上游是 `rag.py` / `agent.py`（融合后调用它）；下游是 `llm.py` 的 `complete_chat`（非流式补全）。
- **为什么这么设计**：
  - **绝不成为单点故障**：任何失败（模型没配、超时、返回非法 JSON）都只让 `rerank_applied=False`，退回 RRF 原序继续；
  - `_RERANK_MAX_TOKENS=3072` 是踩坑来的——推理型模型会先把预算花在「思维链」上，给小了会 `finish_reason=length` 且正文为空，
    排序结果拿不到、白白降级；
  - `rerank_timeout=45` 同理（20 秒时模型还没想完就被掐断，造成**静默降级**，极难发现）；
  - `_summarize` 压缩提示词、省 token。
- **读这一遍必须能回答的面试问题**：
  1. RRF 只看排名不看内容，重排补上了什么？
  2. 为什么重排失败要「静默退回原序」而不是报错？
  3. 为什么给重排的 `max_tokens` 要给到 3072 而不是几百？

### 14. `backend/app/deep_agent.py` —— Plan-and-Solve / Deep（含 Reflection）
**链路归属：问答链路（`/api/agent/chat` 的 `plan` / `deep` 模式）**

- **一句话职责**：用**手写 async 编排**（不用 LangGraph `StateGraph`）实现「先规划、再逐步解决、再自评改进」的复杂问答。
- **关键函数**：

  | 函数 | 签名 | 输入 | 输出 |
  |---|---|---|---|
  | `_dedupe_sources` | `_dedupe_sources(sources: list[dict[str, Any]]) -> list[dict[str, Any]]` | 多步来源 | 去重后的来源 |
  | `_merge_meta` | `_merge_meta(metas, final_count: int, s: Settings) -> dict[str, Any]` | 各步 meta、条数、配置 | 合并后的检索 meta |
  | `_plan_messages` | `_plan_messages(question: str, s: Settings) -> list[dict[str, str]]` | 问题、配置 | 规划提示消息 |
  | `_parse_plan` | `_parse_plan(raw: str, question: str, max_steps: int) -> list[dict[str, str]]` | 模型输出、问题、最大步数 | 子任务列表（解析失败则用兜底计划） |
  | `_step_instruction` | `_step_instruction(question: str, step, index: int, total: int) -> str` | 问题、子任务、序号 | 单步执行指令 |
  | `_solve_messages` | `_solve_messages(...)` | 问题、子任务、观察 | 求解提示消息 |
  | `_reflect_messages` | `_reflect_messages(...)` | 草稿、来源 | 自评提示消息 |

  | `run_deep_events` | `async run_deep_events(question: str, settings=None, final_k: int | None = None, mode: str = "plan", web_search: bool | None = None) -> AsyncIterator[dict[str, Any]]` | 问题、配置、模式、联网 | 事件流（额外发 `plan` / `plan_step` / `reflection`；`delta` 带 `channel`） |

- **上游 / 下游**：上游是 `agent.py` 的 `agent_events`（plan/deep 委托进来）；下游是 `llm.py`、`retriever.py`。
  从 `agent.py` 复用了 `_build_agent`、`_citation_check`、`_new_states`、`_new_turn_state`、`_snapshot_rag_state`、`_stream_react_turn`。
- **为什么这么设计**（**重要设计取舍**）：
  - 明确**不用 LangGraph 的 `StateGraph`**：`StateGraph` 的 `messages` 流会把子图每一步的 `AIMessage` 全部「冒泡」上来，
    只能事后按 `metadata.langgraph_node` 过滤——过滤错一次，规划文本就会漏进用户看到的正文里；
    本项目已被 langchain/langgraph 的版本行为坑过两次，所以 plan/deep 改成**显式 async 编排**，完全自己掌控「哪句话该给用户看」；
  - `delta` 增加 `channel` 字段区分「正文」和「修订稿」；
  - 规划解析失败有兜底计划、自评失败有兜底回答，仍然贯彻「降级不崩溃」。

  1. Plan-and-Solve 相比 ReAct 多了什么？Reflection 又是什么？
  2. 为什么这里**不**用 LangGraph 的 `StateGraph`？「messages 冒泡」是什么问题？
  3. `delta.channel` 为什么需要区分 `answer` 和 `revision`？

#### 15.1 `pg.py` —— 自然语言转只读 SQL（PostgreSQL）
- **一句话职责**：把「预算超 100 万的项目有几个」这类问题，转成只读 SQL 去 PostgreSQL 查精确统计。

  | `_connect` | `_connect(s: Settings, readonly: bool = True)` | 配置、是否只读 | 只读连接 |
  | `load_schema` | `load_schema(s: Settings, refresh: bool = False) -> dict[str, Any]` | 配置、是否强制刷新 | 库结构 |
  | `render_schema_text` | `render_schema_text(data: dict[str, Any]) -> str` | 库结构 | 给模型看的结构文本 |
  | `build_sql_messages` | `build_sql_messages(question: str, schema_text: str, max_rows: int) -> list[dict[str, str]]` | 问题、结构、行数上限 | 提示消息 |
  | `clean_sql` | `clean_sql(raw: str) -> str` | 模型输出 | 清理后的 SQL |
  | `validate_sql` | `validate_sql(sql: str, max_rows: int) -> str` | SQL、行数上限 | 校验通过并强制加 LIMIT 的 SQL（不合规抛错） |
  | `run_query` | `run_query(s: Settings, sql: str) -> tuple[list[str], list[tuple[Any, ...]]]` | 配置、SQL | (列名, 行元组列表) |
  | `render_result` | `render_result(sql, columns, rows) -> str` | SQL、列、行 | 给模型看的结果文本 |

#### 15.2 `graph.py` —— 自然语言转只读 Cypher（Neo4j）
- **一句话职责**：把「这家公司中标了哪些项目」这类关系/多跳问题，转成只读 Cypher 去 Neo4j 图谱查。
- **关键函数**：`_get_driver`、`_session`、`_read_rows(s, cypher) -> list[dict]`、`load_schema(s, refresh=False)`、
  `render_schema_text(data)`、`build_cypher_messages(...)`、`clean_cypher(raw)`、`validate_cypher(cypher: str, max_rows: int) -> str`、
  `run_query(s, cypher) -> list[dict[str, Any]]`、`render_result(cypher, rows) -> str`、`_run_graph(...)`、
  `async query_bidding_graph(question: str, config: RunnableConfig) -> str`（`@tool`）。
  工具名常量：`GRAPH_TOOL_NAME = "query_bidding_graph"`；`_CELL_TEXT_LIMIT=300`、`_ROWS_TO_STATE=20`。
  只读靠 `session.execute_read(...)`。

#### 15.3 `web_search.py` —— Tavily 联网搜索
- **一句话职责**：本地知识库查不到时，去公开互联网补最新公告/法规，结果带相关性评分交回模型。
- **关键函数**：`_search(query: str, settings: Settings, max_results: int) -> list[dict[str, Any]]`、
  `render_results(...)`、`async search_web_bidding(...)`（`@tool`）、`class WebSearchError(RuntimeError)`。
  常量：`TOOL_NAME = "search_web_bidding"`、`DEFAULT_MAX_RESULTS = 5`、`_SNIPPET_CHARS = 800`。

- **上游 / 下游**：三者都被 `agent.py`/`main.py` 注册成 Agent 工具（**只有配置齐备才注册**）；下游分别是 PG / Neo4j / Tavily。
- **为什么这么设计**：
  - 不同问题需要不同存储形态：语义检索、精确统计（PG）、多跳关系（Neo4j）各管一摊；
  - **三层只读保护**：大模型生成的 SQL/Cypher 不可信任，必须服务端只读事务 + 静态关键字拦截 + 单语句 + 强制 LIMIT；
  - 联网搜索**不配 Key 就干脆不注册工具**，让用户「不会以为开了联网却搜不到」；搜索失败只记错误、返回提示，绝不让整轮问答失败。
- **读这一遍必须能回答的面试问题**：
  1. 让大模型生成 SQL 去查生产库，安全上要怎么防？（说出三层）
  2. 为什么工具「没配置就不注册」，而不是「注册了再报错」？

### 16. 支撑模块：`answer_cache.py` / `metrics.py` / `logging_setup.py`
**链路归属：问答链路的「旁路」与「地基」**

#### 16.1 `answer_cache.py` —— 问答结果缓存（规范化精确匹配）
- **一句话职责**：对完全重复的提问，直接回放缓存答案，省一次大模型调用；命中判断和读写都极保守、失败静默。
- **关键函数**：

  | 函数 | 签名 | 输入 | 输出 |
  |---|---|---|---|
  | `normalize_question` | `normalize_question(question: str) -> str` | 问题 | 规范化后的缓存主键（NFKC 全角转半角 → 去空白 → 转小写 → 连续空白压一个空格） |
  | `cache_key` | `cache_key(question: str) -> str` | 问题 | 缓存键 |
  | `looks_sensitive` | `looks_sensitive(question: str) -> bool` | 问题 | 是否疑似敏感（敏感不进缓存） |
  | `is_cacheable` | `is_cacheable(*, logged_in: bool, mode: str = "react", has_history: bool = False, web_search: bool = False, has_image: bool = False, question: str = "") -> bool` | 各种标志 | 是否该进缓存（读写共用同一准绳） |
  | `get_cached` | `get_cached(question: str, settings=None) -> dict[str, Any] | None` | 问题、配置 | 缓存命中则返回 {答案+来源}，否则 None |
  | `set_cached` | `set_cached(question: str, answer: str, sources, mode: str, settings=None) -> bool` | 问题、答案、来源、模式 | 是否写入成功（失败静默 False） |

- **为什么这么设计**：采用**规范化精确匹配**而非语义匹配——语义匹配容易「张冠李戴」（把 A 的答案给 B）。
  代价是「近义改写永远不命中」，收益主要来自完全重复的提问；命中错比不命中更致命。
  排除：未登录、`mode=="deep"`、带多轮历史、开联网、带图片、疑似敏感。所有读写失败一律静默降级。

#### 16.2 `metrics.py` —— 问答指标
- **一句话职责**：把每次问答的耗时、首字延迟、来源数、是否命中缓存/重排等记进 SQLite，供 `/api/metrics` 汇总。
- **关键函数**：`record(*, mode: str, elapsed_ms: float, first_token_ms=None, sources_count: int = 0, cache_hit: bool = False, rerank_applied: bool = False, settings=None) -> bool`、
  `summary(settings=None) -> dict[str, Any]`；建表 SQL 常量 `_DDL`。
- **为什么这么设计**：**静默降级**——观测埋点绝不能影响主流程，成功返回 `True`、任何失败静默返回 `False`。

#### 16.3 `logging_setup.py` —— 日志初始化
- **一句话职责**：幂等地配置全局日志（等级来自配置），并给出统一取 logger 的入口。
- **关键函数**：`setup_logging(settings=None) -> None`（线程锁保证只配置一次）、`get_logger(name: str = ...) -> logging.Logger`。

- **上游 / 下游**：`answer_cache` 由 `main.py` 的 `/api/chat` 调用；`metrics` 由 `main.py` 的 `_finalize_qa` 调用；
  `logging_setup` 在服务启动时调用。
- **读这一遍必须能回答的面试问题**：
  1. 缓存为什么用「精确匹配」而不是「语义匹配」？各自的风险是什么？
  2. `is_cacheable` 排除了哪些请求，为什么？
  3. 为什么指标/缓存/日志都要「失败静默」，不对主流程抛异常？

### 17. 辅助模块（按任务的补充要求，放入对应链路的说明）

#### 17.1 `backend/app/auth.py` —— 账号与令牌（问答链路 / 历史落库的前置）
- **一句话职责**：用 PBKDF2-HMAC-SHA256 存口令、签发/校验令牌，并做登录失败锁定。
- **关键函数**：`hash_password(password: str, iterations: int) -> tuple[str, str]`（返回 哈希, 盐）、
  `verify_password(password, salt_hex, iterations, expected_hash) -> bool`、`validate_credentials(username, password) -> None`、
  `issue_token(settings, user_id, user_agent) -> str`、`resolve_token(settings, raw) -> dict | None`、`revoke_token(settings, raw) -> None`、
  `register(...)`、`login(...)`、`logout(settings, raw) -> None`、`optional_user(...)`、`current_user(...)`、`require_bearer(...)`、
  `class AuthError` / `RateLimited` / `AuthUnavailable`。
- **为什么这么设计**：每用户独立随机盐 + `hmac.compare_digest` 常量时间比较（防时序攻击）；令牌只存其 SHA-256（库里泄露也拿不到原令牌）；
  进程内锁定（连续失败锁定一段时间）。`optional_user` 让接口「登录可选」（未登录照样问答，只是不缓存/不落库）。

#### 17.2 `backend/app/history.py` —— 对话历史（问答链路写、后台读）
- **一句话职责**：用 SQLite（WAL + FTS5）存用户、会话、消息，支持中文全文检索（FTS5 不可用时降级 `LIKE`）。
- **关键函数**：`ensure_schema(settings=None) -> None`、`fts_available(settings=None) -> bool`、`create_user(...)`、`get_user_by_username(...)`、
  `create_session(...)`、`get_session_user(...)`、`delete_session(...)`、`purge_expired_sessions(...)`、`create_conversation(...)`、
  `ensure_conversation(...)`、`list_conversations(...)`、`rename_conversation(...)`、`delete_conversation(...)`、`append_message(...)`、
  `list_messages(...)`、`search_messages(...)`、`_search_like(...)`、`_build_preview(content, tokens) -> str`、`_index_terms(text) -> list[str]`、
  `_match_expression(tokens) -> str`、`stats(settings=None) -> dict`。
- **为什么这么设计**：FTS5 默认 `unicode61` 分词器**不切中文**，所以专门存一列 `seg`（jieba 分词结果，复用 `bm25.tokenize`），查询时先分词再 `MATCH`；
  预览不用 FTS5 的 `snippet()`（外部内容表下只能读到分词后的 `seg`，展示难看），改成从原文截取、手工插 `<em>` 高亮；
  FTS5 不可用时回落 `LIKE`——「慢但保证搜索永远可用」。

#### 17.3 `backend/app/vision.py` —— 图片解析（问答链路的前置）
- **一句话职责**：把用户上传的招标公告截图交给智谱视觉模型识别成文字。
- **关键函数**：`resolve_mime(filename: str | None, content_type: str | None) -> str`（都不支持则抛 `ImageRejected`）、
  `check_size(size: int, settings: Settings) -> None`（空/超限抛 `ImageRejected`）、`analyze_image(...)`；
  异常 `class ImageRejected(ValueError)`（→ HTTP 400）、`class VisionError(RuntimeError)`（→ HTTP 502）。
  常量：`_EXT_MIME`、`_ALLOWED_MIME`、`DEFAULT_PROMPT`。
- **为什么这么设计**：区分「用户图片不行的 400」和「服务侧上游模型出问题的 502」；未配 Key / 模型报错统一 502。

#### 17.4 `backend/app/embeddings.py` 与 `ingest.py`
- 已分别在第 6 节、第 4 节详细展开（它们正是建库链路两端的主角）。

#### 17.5 独立同步脚本（建库/运维，人工在命令行执行）
- `backend/copy_mysql.py`（远程 MySQL → 本机 MySQL，数据留底）、`backend/sync_pg.py`（远程 MySQL → 本机 PostgreSQL，供统计查询）、
  `backend/import_neo4j.py`（远程 MySQL → Neo4j 图谱，供关系查询）。
- **为什么这么设计**：不同问题需要不同存储形态，三者各管一摊，所以没合并成一个通用 ETL；
  脚本都由人工执行，后端服务**不会自动调用**。

  关键签名：
  - `chat(payload: ChatRequest, user: dict[str, Any] | None = Depends(auth.optional_user)) -> StreamingResponse`
  - `async agent_chat(payload: AgentChatRequest, request: Request, user: dict[str, Any] | None = Depends(auth.optional_user)) -> StreamingResponse`
  - `def retrieve_only(...)`（`GET /api/retrieve`，默认不重排，带 `rerank=true` 才调模型）
  - `def start_ingest(payload: IngestRequest, user: dict[str, Any] = Depends(auth.current_user)) -> dict[str, Any]`（**要求登录**）

- **上游 / 下游**：上游是前端 / curl / 后台页；下游是所有业务模块。
  `/api/chat` 走 `answer_cache`（可选命中）→ `rag.answer_events`；`/api/agent/chat` 走 `agent.agent_events`（plan/deep 转 `deep_agent`）。
- **为什么这么设计**：
  - `/api/chat` 用 `optional_user`（登录可选）：未登录照样问答，只是不缓存、不落库——**向后兼容**；
  - `/api/ingest` 要求登录（重建是高危运维动作），且 `mode` 与 `recreate` 必须成对：「增量不允许 `recreate=true`」（400，增量不能重建集合）、「全量不允许 `recreate=false`」（400，否则已删数据不会清理）；「已有任务运行返回 409」；
  - SSE 用 `ensure_ascii=False` 保证中文不被转义成 `\uXXXX`；
  - 落库/缓存/指标全部「失败不影响问答流」。
- **读这一遍必须能回答的面试问题**：

  3. 为什么「重建知识库」接口要求登录、还限制并发？

### 19. `frontend/lib/api.ts` —— 接口封装与 SSE 解析
**链路归属：问答链路（前端侧）**

- **一句话职责**：统一封装后端接口、管理登录令牌，并实现把后端 SSE 响应解析成 `ChatEvent` 的异步生成器。
- **关键函数 / 结构**：

  | 名称 | 签名 | 输入 | 输出 |
  |---|---|---|---|
  | `parseSSEBlock` | `parseSSEBlock(block: string): ChatEvent | "[DONE]" | null` | 一个已按空行切开的 SSE 块 | 解析出的事件；`"[DONE]"` 表示流结束；`null` 表示可跳过 |
  | `readSSE` | `async function* readSSE(res: Response): AsyncGenerator<ChatEvent>` | fetch 响应 | 逐条产出 `ChatEvent`（`/api/chat` 与 `/api/agent/chat` 共用） |
  | `streamChat` | `async function* streamChat(question: string, topK?: number, signal?: AbortSignal): AsyncGenerator<ChatEvent>` | 问题、条数、中断信号 | 事件流（POST `/api/chat`） |
  | `streamAgentChat` | `async function* streamAgentChat(question: string, history: ChatTurn[] = [], topK?: number, webSearch?: boolean, mode?: ChatMode, conversationId?: string | null, signal?: AbortSignal): AsyncGenerator<ChatEvent>` | 问题、历史、条数、联网、模式、会话 id、中断信号 | 事件流（POST `/api/agent/chat`，已登录自动带 Bearer） |
  | `analyzeImage` | `async function analyzeImage(file: File, question?: string): Promise<ImageAnalysis>` | 图片、可选提问 | 识别结果 |
  | `api` | `const api = { health, config, schema, kbStats, startIngest, ingestStatus, register, login, logout, me, ... }` | —— | 各接口封装 |
  | 令牌工具 | `getToken()` / `setToken()` / `clearToken()`，键 `TOKEN_KEY="bidding.token"` | —— | 读写本地令牌 |

  `ChatEvent` 是一个**联合类型**（union），涵盖 `retrieval` / `sources` / `delta` / `done` / `error` / `conversation` /
  `plan` / `plan_step` / `reflection` / `tool_call` / `tool_result` / `sql_query` / `graph_query` / `web_search` / `citation_check`。

- **上游 / 下游**：上游是 `app/page.tsx`（对话页）；下游是后端 HTTP/SSE 接口。
- **为什么这么设计**：
  - SSE 的解析要点：`\r\n` 归一成 `\n`、按空行切事件、一个事件可有多行 `data:` 需用 `\n` 拼接、`[DONE]` 表示结束；
  - `readSSE` 用 `try/finally` 保证无论正常结束 / `[DONE]` / 抛错 / 被 abort，都 `cancel()` + `releaseLock()`，避免连接与锁泄漏；
  - `streamAgentChat` 已登录时自动带令牌，后端才会落库。
- **读这一遍必须能回答的面试问题**：
  1. 浏览器是怎么从 `text/event-stream` 里一条条解析出事件的？多行 `data:` 怎么处理？
  2. 为什么解析函数要返回 `"[DONE]"` 而不是直接结束？
  3. 为什么读流结束一定要 `releaseLock()`？

### 20. `frontend/app/page.tsx` —— 对话页状态机
**链路归属：问答链路（前端侧）**

- **一句话职责**：主对话页，持有全部 UI 状态，驱动一次问答的发送与事件消费，把 `ChatEvent` 应用到消息对象上。
- **关键结构**：
  - `useState` 状态：`health`、`kb`、`banner`、`messages`、`input`、`busy`、`imageFile`、`imageUrl`、`analyzing`、`webSearch`、`mode`、`user`、`authOpen`、`conversationId`、`historyRefreshKey`、`highlightId`、`railOpen`……
  - `runSend(text, base?)`（`useCallback`）：一次发送的核心流程；每个请求配一个 `AbortController`（`abortRef`），新建对话/切会话/卸载时中断旧流，避免「旧流串台」。
  - 事件处理：用 `if/else if` 链逐类处理 `conversation` / `retrieval` / `sources` / `delta` / `plan` / `plan_step` / `reflection` /
    `tool_call` / `tool_result` / `sql_query` / `graph_query` / `web_search` / `citation_check` / `done` / `error`，
    统一通过 `patch((msg) => ({...msg, ...}))` 增量更新消息对象。
  - **流式节流**：`delta` 不逐 token 落库，先攒进 `deltaBufRef`（正文 / revision 两通道各自累计），
    由 `flushTimerRef` 定时冲刷——窗口 **≥50ms**；正文超过 6000 字符后自适应拉长到 **120ms**（长回答下 Markdown 重解析是最大开销）。
    `done` / `error` / 中断时 `flushNow()` 立即冲刷，保证尾巴不丢；切会话 / 新建对话时 `clearDeltaQueue()` 丢弃旧流缓冲。
  - **滚动管理**：`atBottomRef` 记录是否贴底（距底 80px 内），`onScroll` 维护两个浮动按钮
    （`showJumpLatest` / `showJumpTop`）；messages 变化时只有贴底才跟随（直接改 `scrollTop`，不用 smooth，避免高频排队）。
    `jumpToBottom` / `jumpToTop` 分别对应「回到最新」「回到顶部」。
  - **证据面板接线**：state `evidence = {msgId, size, index, nonce}`；`openEvidence(i)` 找到最后一条来源数足够的助手消息、
    展为半屏并按 nonce 触发定位；`changeEvSize` / `closeEvidence` 控制尺寸与收起。无显式状态时默认折叠条。
  - 联网开关：`canWebSearch = Boolean(health?.web_search_configured)`、`webSearchOn = canWebSearch && (webSearch ?? health?.web_search_default ?? false)`。
- **上游 / 下游**：上游是浏览器用户交互；下游是 `lib/api.ts`（发起请求）与各 UI 子组件（`chat/`、`EvidencePanel` 等）。
- **为什么这么设计**：前端是**无状态**的——多轮历史由前端持有、每轮回传后端（`history`），后端不保存会话上下文；
  这让后端可以水平扩展（虽然本项目的向量库单进程限制暂时做不到多进程）。`AbortController` 保证「切会话/重发」时旧流被正确取消。
- **读这一遍必须能回答的面试问题**：
  1. 前端是怎么把一串 SSE 事件「贴」到同一条助手消息上的？
  2. `AbortController` 在这里解决什么问题？
  3. 为什么对话历史要放在前端持有、每轮回传，而不是后端存上下文？
  4. 流式输出为什么要做 ≥50ms 节流、自适应 120ms 窗口解决什么问题？滚动跟随为什么只在贴底时生效？

## 附二：文档与实现不一致的地方

> 以下都是「README / 注释 里的话」与「代码真实行为」对不上的地方，逐一列出，供你核对时不被误导。

1. **README 把 LangGraph 说成「把 ReAct 循环显式建模成状态图」——与实现不符。**
   README「技术栈与选型理由」表中写「LangGraph / 把 ReAct 循环显式建模成状态图」。
   实际代码里：`agent.py` 用的是 **`langgraph.prebuilt.create_react_agent`**（预构建的 Agent，并非自己搭 `StateGraph`）；
   而 `deep_agent.py` 的注释**明确写着**「为什么是『显式 async 编排』而不是新建 LangGraph StateGraph」，
   即 plan/deep 模式根本**不用** `StateGraph`。所以「显式建模成状态图」这个说法只对「底层库内部」成立，
   对自己的代码并不成立。

2. **README 架构图把「招投标法规文件」画成数据源——与实现不符。**
   README 的 mermaid 与纯文本架构图里，数据源标注为「MySQL 业务库……＋ 招投标法规文件」。
   实际 `ingest.py` 只从 MySQL（或 `KB_SOURCE=postgres` 的本机 PG 副本）读取；
   **没有任何读取「法规文件」的代码路径**。README 正文自己也补了一句「『法规文件』也可复用同一条管线接入（扩展点）」——
   即它只是设想，不是已实现能力。

3. **配置项注释与代码默认值不符：`LLM_MAX_TOKENS`。**
   `config.py` 中 `llm_max_tokens` 字段的注释写「实际部署调大到了 **3072**」，
   但同一文件里 `_build_settings` 的代码是 `llm_max_tokens=_int("LLM_MAX_TOKENS", 1024)`——**默认值仍是 1024**，
   `.env.example` 里也是 `LLM_MAX_TOKENS=1024`。注释说的是「部署时改过的值」，代码默认值并没跟着改，
   直接读代码会以为默认是 3072。

4. **有两套「向量化批大小」，容易混淆。**
   项目里其实有**两层**批大小，名字相近但用途不同：
   - `config.py` 的配置项 `embed_batch_size`（默认 **32**）——在 `embeddings.py` 里传给 fastembed，
     控制**模型内部**一次处理多少段文字（`self.model.embed(texts, batch_size=self._settings.embed_batch_size)`）；
   - `ingest.py` 里**硬编码的常量** `_EMBED_BATCH = 64`——控制建库时**外层循环**每批处理多少篇文档（用于进度打印与分批写入）。
   也就是说调 `EMBED_BATCH_SIZE` 只会改变模型内部批大小，**不会**改变建库外层循环的分批（那由写死的 64 决定）——
   两个「batch」若混着理解，就会出现「改了没反应」的困惑。

5. **README 的「关键参数说明」表未收录 `LLM_MODEL_DISPLAY`。**
   `config.py` 提供 `llm_display_name`（来自 `LLM_MODEL_DISPLAY`，默认空），`main.py` 的 `/api/health` 会回显为
   `llm_model_display`，前端后台页「对话模型」卡片优先显示它。这是「界面展示名可与真实 API model id 不同」的机制，
   但 README 的参数表里没有它。

6. **README 架构图把「LLM 重排」画成必经阶段——实现上是「可失败、可退化」的。**
   README 架构图 `QD --> MIX --> RE --> AG` 把重排画成链路上固定的一环。
   实际 `rerank_hits` 在任何失败时都只令 `rerank_applied=False`、**退回 RRF 原序**（README 参数表与评测注里确实提到了
   「静默降级」，但图本身没有体现「可能不生效」）。另外 README 评测表里 A/B/C 三档配置的 recall 有差异，
   但 MRR 在 B、C 两档完全相同（都是 0.833），说明该评测集上重排并未带来 MRR 提升（README 也注明「重排本集仅 4/10 生效」）。
